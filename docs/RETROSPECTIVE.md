## 2. 技术坑库（一坑一格：现象 → 根因 → 修复 → 防回归）

### 2.1 网络层（M2）

| 坑 | 现象（可观测） | 根因 | 修复 | 防回归 | 出处 |
|---|---|---|---|---|---|
| **发送块级乱序** ✅ | 100MB 回显 `cmp` 不一致；字节数对、内容错位，首个错位量 k ≈ 队列尾巴大小（**4224 / 25536 / 750272**） | `Session::send` 在**发送队列非空时仍直写 socket**；socket 是 FIFO，新块插到队列旧块前面 | 仅 `_send_queue->empty()` 时才直写，否则整段入队 | 确定性用例 `ntimed_send_order_with_backlog`：修前首个 `'B'` 在偏移 **16384**，修后正好 **1048576** 且其后不再出现 `'A'` | `DESIGN_M2.md:754`、`:786`；`CHANGELOG.md:94` |
| **fd 号复用 → 连接全废** ✅ | 新连接 `addEvent` 被判"fd=8 已注册，拒绝重复添加" | `shutdown` 在 `delEvent` 后**立刻 `close(fd)`**，而 poller 是延迟删除 → 内核把同一 fd 号发给新连接 | `close` 只在 `delEvent` 的 `complete_cb` 里做；投递不进去才就地关 | 用例 `ntimed_fd_recycle`（NFR-6 资源回收） | `DESIGN_M2.md:785` |
| **`EPOLLOUT` 从未派发** ✅ | 积压数据只能靠后续读操作"顺带"写出，尾包长期不发 | 读写共用一个回调，`onReadEvent` **只判 `EventRead`** | 改为按位分发 `onEvent` | 发送类用例（`ntimed_session_send_blocked` / 回显往返） | `CHANGELOG.md:86` |
| **ET 写一次就停** ✅ | 尾部数据永远发不出去 | ET 模式下写路径没循环到 `EAGAIN` | 写循环到 `EAGAIN` | 同上 | `CHANGELOG.md:88` |
| **无流控，队列被顶爆** ✅ | 一个读事件读 64MB，把 8MB 发送上限顶穿 | 只设了上限、没有背压 | 发送队列 ≥ `maxSendBuffer/2` 停收，< `/4` 恢复（`modifyEvent` 重挂 `EPOLLIN`） | `ntimed_session_send_overflow` / `ntimed_session_recv_overflow` | `DESIGN_M2.md:787` |
| **超长延时 → 定时器静默永不触发** ✅ | 大 delay 的定时器永远不触发，且**无任何告警** | `minDelayInLoop` 里 `next - now` 越过 int64 上界后 `static_cast<int64_t>` 得负数 → 被当成"没有定时器" → `epoll_wait` 永久等待 | 差值**饱和**到 `INT64_MAX`，再交给 `clampTimeout` 截断 + 计数 + 告警 | 边界用例 `timer_huge_delay_clamped`（修前为红） | `DESIGN_M2.md:747`；`CHANGELOG.md:45` |
| **`doDelayTask` 退出后返回非空 handle** ✅ | 调用方以为排上了，实际永不触发（**静默降级**） | 轮询线程内的路径没检查 `_exit`，与跨线程路径语义不一致 | 已退出一律返回 `nullptr` + `rejectedTimerCount()` | 用例 `timer_submit_after_shutdown` | `DESIGN_M2.md:775` |
| **clamp 告警刷屏** ✅ | 一条超长定时器把日志刷爆，真问题被淹 | Warn 每轮事件循环都打 | Warn 只在**进入**截断状态时打一次，计数仍逐次累加 | 计数 `timeoutClampCount()` 可观测 | `DESIGN_M2.md:771` |
| **同刻大量到期 / 0 延时自投链占住事件循环** ✅（只观测） | 1000 个同刻到期 = 1 批 1000 个；20 步 0 延时自投 = 1 批 20 个（期间不派发 epoll、不检查退出） | `processDelayTask` 一轮处理完一批 | **先观测、暂不限制**（新增 `delayBatchMax()` / `delayBatchCount()`）；改判条件：线上单批远超客户端数 | 用例 `timer_reentrant_zero_delay` | `DESIGN_M2.md:753`、`:776` |
| **精度门禁在虚拟化宿主上不可达** ✅ | `timer_precision` 113ms > 110ms 翻红，但**与被测对象无关** | 宿主 tick 量化唤醒延迟 **0~14ms 且与延时长短无关**（裸 `nanosleep` 10ms/100ms/1s 档实测 +6 / +10 / +13） | 门禁改为"**0 早触发** + 相对同进程裸基线增量 ≤5ms"，对拍取**最小值**剔除随机噪声 | 用例 `timer_precision`；TSAN 构建按编译期判定放宽到 25ms | `DESIGN_M2.md:751`、`:770`；`CHANGELOG.md:38` |
| **真实竞态：同步对象生存期** ✅ | TSAN 报 `pthread_cond_destroy` vs `pthread_cond_broadcast` | `timer_precision` 把 `Semaphore` 声明在**循环里**，上一轮析构与轮询线程仍在进行的 `post()` 并发 | 等待用的同步对象必须活得比它等待的线程长；提到 `poller->shutdown()` 之后 | 规矩写入 `TESTING.md` §8.7 | `TESTING.md:213`；`CHANGELOG.md:61` |
| **测试框架自伤：汇总行单位混淆** ✅ | 输出"用例 18 个（通过 16 / 失败 3）"这种自相矛盾的行 | "失败"打的是**断言**数，却与"通过"的**用例**数并列 | 两处都写明单位（`failed_cases`） | 框架自测组 `selftest` | `CHANGELOG.md:59` |

### 2.4 ✅ 测试之间不隔离（已修，2026-10-03）

| 项 | 内容 |
|---|---|
| **现象** | 从仓库根跑**单进程全量** `./build/bin/mzmedia_unittest`：修前 **171 用例中 8 个红**（全是依赖样本相对路径的 ffmpeg 用例：`ffmpeg_demux_*` 6 个 + `ffmpeg_h264_extract_from_raw_sample` + `ffmpeg_h264_sps_dimension_matches_demuxer`）；修后这 8 个**全部转绿** |
| **误导性** | 失败信息是"找不到样本 sample.h264（试过 3 个路径，请先跑 scripts/make_samples.sh）" → **把人指向错的因**：样本文件其实一直都在（`ls -l samples/` 四个文件俱在，重建前后大小完全相同） |
| **根因** | `util_file_relative` 与 `logger_file_relative_path` 收尾用 `::chdir("/")`，**而不是切回进入前的目录** → 进程工作目录被永久改成 `/`，之后所有相对路径（`samples/`、`../samples/`、`../../samples/`）都以 `/` 为基准。真凶 2 个用例，锅扣在 8 个无辜用例头上 |
| **为什么一直没被发现** | `ctest` 的**每个分组是独立进程**，`util` / `logger` 与 `ffmpeg` 永不同进程 → 全绿；只有"单进程跑全部用例"这条路径才暴露 |
| **为什么这次才抓到** | 此前引用全量结果时**只看了汇总行的"用例数"，没看"失败数"**（我的错，见 §5.3） |
| **修法（已实施）** | ① `tests/test_main.h` 新增 `::mztest::ScopedCwd`（RAII 还原工作目录）；② **框架级不变量**：用例结束时工作目录被改动 ⇒ 当场点名该用例 + 立刻还原（不再让下一个用例背锅）；③ 两个真凶改用 `ScopedCwd`；④ 样本查找改为与工作目录无关（向上最多 8 层） |
| **防回归** | `selftest_scoped_cwd_restores`（锁守卫本身）+ `ffmpeg_samples_found_from_nested_cwd`（**变异验证**：把搜索层数改成 2 即红，报错正是原始症状） |
| **教训（可复用）** | ① 跨用例的隐式全局状态（cwd / 环境变量 / fd / 信号）一出事，**报错会落在无辜者身上**，所以这类不变量该由**框架**检，不该指望用例自觉；② `ctest` 每个分组独立进程＝**天然隔离**，也意味着它**看不见**用例之间的串味 |
| **遗留（另案）** | 同一个全量跑里还剩 `timer_precision` 红：那是**计时门禁**在单进程上下文下的抖动（单独跑 6/6 绿，差 1ms）→ 规矩记入 `docs/TESTING.md` §2.2 |

### 2.5 ✅ M5-c：订阅管理不是线程安全的（TSAN 抓到 **13 处真竞态**）

| 项 | 内容 |
|---|---|
| **现象** | 接上真实源线程后，TSAN 严格组首次跑 `srcmgr` 就报 **13 处 `data race`**（**不是**已知误报 —— 报告里没有"双方都持锁"的标注） |
| **根因** | `MediaSource` 从 M5-a 起就写着"只在源线程调用"，M5-b 只给它加了**队列锁**；M5-c 让调用方在**源线程推流的同时** `subscribe()`，而 `subscribe()` 要读 `GopCache`（源线程正在 `feed()`）→ 两边完全没有同步 |
| **为什么之前没暴露** | M5-a/M5-b 的用例要么单线程驱动，要么"先 subscribe 再推流"——**没有一条用例让两者并发** |
| **修法** | 订阅集合 / `GopCache` / `_ended` / `_next_id` 统一由 `MediaSource::_mutex` 保护；**唤醒移到锁外**（`async` 在轮询线程上会**内联执行** drain 回调 → 锁内唤醒 = 重入死锁）；唤醒清单改**局部** vector（成员暂存会被两个线程的调用互相清空）；`Subscriber::broken()` 改 atomic |
| **教训（可复用）** | "这个类只在 X 线程用"是**会过期**的约定 —— 一旦有第二个线程进来（哪怕只是"读一下缓存"），约定就失效了。**约定必须配一个能自动发现它失效的机制**；这里就是 TSAN 严格组。它在本项目已经第 2 次立功（第 1 次是 `Semaphore` 生存期，见 §2.1） |

### 2.6 ✅ M6-c：三个"单测全绿、串起来才红"的问题（2026-10-07）

同一个批次里出现三类**不同来源**的缺陷，正好凑齐"怎么才能发现它们"的三种手段：

| # | 现象 | 发现手段 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | 源读完之后**再拉同一路**，连接一直挂着不动（客户端：连上、头发了、然后永远黑屏） | **端到端脚本**（`scripts/flv_http_test.sh` §8：修前 `curl rc=28` 挂满 8 秒超时） | 晚到订阅者的队列在 `subscribe()` 里就 `markEndOfStream()`，但那一刻 drain 回调**还没注册**（由 `FlvSender::create()` 稍后注册）→ 永远不会有唤醒 | `FlvSender::start()` 发完头**立刻搬一次队列**（顺带解决"中途接入的 GOP 缓存要立刻发"） |
| 2 | 循环播放**每 2 秒**被 ffmpeg 报一次 `non monotonically increasing dts` | **端到端脚本**（§9：`ffmpeg -f null -` 有 error 输出）+ 单测里补"音频也要严格递增"的断言 | 偏移量 = 末帧 dts + 帧长，而时间戳是**整数毫秒**：AAC 一帧真实 23.22ms 只能写 23 → 第二趟首包与第一趟末包撞在同一毫秒（差 0.22ms） | 帧长**向上取整** + 额外 **1ms 间隙**；两条流各自断言跨趟严格递增 |
| 3 | **有人正在看**的源也会在 60s 后被释放，观看者突然"播完" | **读代码**（写 app 接线时顺着"句柄什么时候放"读下去发现的；M6-d 的 5 分钟验收必然踩到） | `SourceManager` 的空闲释放只看**句柄数**；应用层 handler 一返回就放掉句柄，而连接还连着、订阅者还在推流 | `subscriberCount() > 0` 就**推迟**（计数 `idle_deferred`）+ 按 `deferred_recheck_ms` 复查；三个入口共用一个守卫 |

**教训（可复用）**：
- 缺陷的"来源"决定发现手段 —— **单元测试擅长证明"组件按我理解的契约工作"，端到端才证明"这些契约拼起来是你想要的东西"**。
  本批 2/3 的问题属于后者，而它们的表现都不是"崩了"，是"看起来在跑，其实不对"（挂住 / 警告刷屏 / 悄悄换了个时刻结束）。
- **"计数为零"要问清楚是谁的计数**：句柄数归零 ≠ 没人看（问题 3）。凡是"生命周期"判断，都要列出**所有**持有者的种类，
  而不是只数其中一种。
- 还有一个**反向**收获：本批我自己先加了一个"循环重开时重置节流基准"的机制（`ReadResult::PacketNewSegment`），
  然后做**反证**（拿掉它，`--loop --speed 4` 拉 3 秒，加/不加都是约 12.0 秒媒体时长）→ 无可观测差别，
  于是**删掉**。这验证了 `AI_COLLAB` 那条纪律的价值：**验证不了的复杂度就是负债**（留着的话，半年后没人敢删）。

## 3. 测量工具与误判（**复用价值最高的一节**）

> 这一节的价值高于 §2：§2 复用的是"某个坑的修法"，这一节复用的是**方法**。

| # | 误判 | 真相 | 教训 | 出处 |
|---|---|---|---|---|
| 1 | "插队 = 0"，所以 `send` 是保序的 | **异步日志未 flush**，看到的"0"是假象 | 结论依赖日志时，先确认日志落盘 | `DESIGN_M2.md:754` |
| 2 | 7.5MB 就 send-overflow，所以回显有缺陷 | `/tmp/probe_echo.cpp` 把 **reader 线程建在发送循环之后**，对端一直不读 → 撑爆队列 | 探针的时序要与被测对象**解耦**，否则探针就是故障源 | 同上 |
| 3 | 测试跑的是新二进制 | `A ; B &` 把**整条命令链**后台化，`cmake --build` 也被后台了 → 测试跑旧二进制 | 后台化要精确到"哪一条命令"，不要用 `A ; B &` | 会话记录（M2-3b） |
| 4 | 测试"失败"其实是把输出接了 `head` | 接了 `head` 之后上游收到 SIGPIPE，**掩盖了真实退出码** | 判据命令一律把输出落文件后再比较，不靠"接 `head` 后的退出码"决定成败 | 会话记录 |
| 5 | Python 校验片段随机翻红 | 片段自身不稳定 | 换成 `cmp`（确定性、逐字节） | `CHANGELOG.md:98` |

## 4. 决策与代价（面试最容易被追问"为什么不做 X"）

> 完整列表在各设计文档的「决策记录」节：`DESIGN_M2.md:756`、`DESIGN_M3.md:102`、`DESIGN_M4.md:92`。
> 下表只挑**有简历价值**的，并额外补一列"代价"——决策记录里没有，但它才是面试的深水区。

| 决策 | 选择 | 排除的选项 | **代价 / 什么条件下会后悔** |
|---|---|---|---|
| Reactor 模型 | 单 Reactor × N + 连接亲和 | 主从 Reactor（多一个 acceptor 线程，收益不足） | 连接固定在某个 poller 上 → 单连接无法用多核；超多连接时负载不均 |
| 触发模式 | **ET 默认** + `EventLT` 可切 | 只做 LT（少一个能讲深的点） | ET 下漏读到 `EAGAIN` = 连接假死（假死比崩溃难查） |
| 跨线程唤醒 | `pipe2` | `eventfd`（无法携带负载）；条件变量（唤不醒 `epoll_wait`） | 多花 2 个 fd |
| 定时器 | `multimap` 最小堆 | 时间轮（实现量翻倍，本项目规模不需要） | 定时器数量级上来后插入是 O(log n) 而非 O(1) |
| 错误模型 | `SockException` 带 `ErrType` | 只看 errno | 多一层枚举维护；但 FR-4.4 的四类断开在 errno 里都是 0/ETIMEDOUT，不分桶就没法计数 |
| 公开接口 **尽量不用 `void`** | 配置 setter 返回"是否生效"；操作返回"实际完成量"；注册回调返回上一个 | void + 文档约定"一定成功" | 接口更啰嗦；被调用的钩子仍保留 `void`（没有接收方语义） |
| **有界性优先于"可观测"** | 所有带容量语义的东西（队列、缓存、连接数、超时、单条消息长度）**先拍一个量级的上限**，宁可过松 | "等实测再定"；"0 = 不限"；"有计数就算有界" | 上限可能过松（漏检半个连接 = 资源泄漏，可补）或过紧（误杀正常流量，不可逆） |
| `processDelayTask` 0 延时自投链 | **只观测、不限制** | 每轮处理上限 + 让出循环（引入"积压时延迟一轮"的新行为） | 回调里 `doDelayTask(0, …)` 链会占住事件循环（已量化：20 步 = 1 批 20 个） |
| 定时器精度门禁 | 相对同进程裸基线 ≤5ms（对拍取最小值） | 绝对 ±10ms（宿主噪声让门禁与被测对象无关地红） | 换裸机后应能收紧回绝对 ±5ms（`DESIGN_M2.md:802` 未决 7） |
| CodecMatrix 的"不知道" | 一律 `Unsupported`（+ErrorP），**绝不默认 Remux** | 默认 Remux（"看起来能用"） | 更保守：HEVC→FLV 直接拒绝；换来的是**不产生"浏览器一片黑"这种极贵故障** |
| SPS 解析契约 | 只承诺**语法**，调用方交叉校验 | 让解析器"猜合法性"（profile 白名单等） | 调用方多一道工序；换掉"对合法但罕见的流误判" |
| 路由配置时机 | 必须 `start()` **之前** | 运行期动态加路由 | 灵活性下降；免掉"路由表被事件循环线程读、另一线程改"的并发问题 |
